# 第1章 为什么需要 GGUF 量化

先从一个数字讲起。一个 7B（70 亿参数）的开源大语言模型，如果用 FP32（每个权重 4 字节）保存，需要约 28 GB 磁盘；换成 FP16（每个权重 2 字节），也要约 14 GB。而一部手机、一台只有 8 GB 内存的笔记本、一块树莓派，物理上就放不下这样的文件。更不要说推理时还要把它整个读进内存了。

量化（quantization）就是回答这个问题的技术：**用更少的比特去表示每个权重，把文件从 14 GB 压到 3–4 GB，同时尽量少地牺牲模型能力**。这里的“比特”就是计算机里最小的信息单位，一个 0 或一个 1；用更少的比特表示一个数，等于让每个数占的地方变小。GGUF 则是这套做法在 llama.cpp 生态里落地的文件格式。它规定了压缩后的权重长什么样，也规定了这些权重怎样存进一个文件、推理时又怎样被读出来。

本章不写任何一行复杂的公式（那部分留给第 2 章），只做三件事。第一，解释端侧部署到底受什么物理条件限制。第二，把“量化”这门语言里最小的一套词汇说清楚。第三，给出全书的路线图，也就是量化格式的三次范式跃迁。读完本章，你应该能回答一个问题：**为什么量化格式不是越简单越好，也不是越复杂越好，而是要分场景选择？**

在正式开始之前，先统一几个术语。**参数（parameter）/ 权重（weight）**：模型在训练时学到的数字，推理时参与矩阵乘法，是文件体积的绝对大头。**推理（inference）**：用训练好的模型做预测。大语言模型的推理通常是“一个字一个字”地往外生成，这里的“字”就是后面要反复出现的 token。**token**：模型处理文本的最小单位，大约相当于“半个词”或者“一个词”。**比特（bit）**：计算机里最小的信息单位，取值为 0 或 1；8 个 bit 合起来是 1 个字节（byte）。**带宽（bandwidth）**：单位时间内能从内存读出多少字节，你可以把它想成一根水管每分钟能流过多少水。**RSS**：进程实际占用的物理内存总量，用来衡量“跑起来到底吃掉多少内存”。


## 1.1 端侧部署的"体积—精度—速度"三角

### 1.1.1 内存带宽是端侧解码的首要瓶颈

大语言模型的推理有一个乍看有点奇怪的物理规律：**模型每生成一个 token，几乎都要把整个模型的权重从内存里读一遍**。你可以顺着它的工作方式想一想：每一步都要算出“下一个 token 是什么”，而这个计算要用到所有层的权重矩阵。权重本身不会一直留在计算单元里，每次都得重新从内存搬到计算单元，搬运量又与模型大小成正比。模型越大，这一步要搬的东西就越多。

于是关键的问题就变成了：**搬运这些权重，到底受什么限制？**是算得不够快，还是别的什么地方先卡住了？

为了回答这个问题，这里引入一个分析工具，叫 **roofline 模型（屋顶线模型）**。它做的事情很朴素：把处理器上的任何一种计算画进一张“屋顶线”图里。横轴是运算强度，也就是每从内存搬运一次数据，能配上多少次算术运算；纵轴是实际能达到的性能。屋顶有两条边。左边那条是**带宽受限**，意思是内存这根“水管”的粗细决定了速度上限；右边那条是**算力受限**，意思是计算单元本身的速度决定了上限。你的任务落在哪一边，瓶颈就在哪一边。

自回归解码的算术强度非常低。所谓“低”，是说每个权重只参与几次乘加运算，算完就暂时没用了，接着要去读下一批权重。也就是说，解码这件事落在 roofline 图的**带宽受限**一侧：

```
roofline 模型：解码落在带宽受限一侧

  性能
   │                      ┌──── 算力上限（FLOPs/s）
   │                ┌─────┘
   │          ┌─────┘
   │    ┌─────┘
   │────┘  ←── 带宽上限（字节/s）
   │
   └────────────────────────────► 运算强度（FLOPs/字节）
       解码任务在这里
       （强度极低 → 带宽受限）
```

这个结论的实操含义非常直接：**端侧能达到的 tok/s（每秒生成的 token 数），约等于"内存带宽 ÷ 每 token 需要读的字节数"**。而每 token 需要读的字节数，等于参数量乘上每个权重占的字节数。把它拆开看，影响速度的因素只有两类：

- 模型越小、每个权重占的字节越少，每生成一个 token 要搬运的数据就越少，tok/s 也就越高；
- 内存带宽越大（通常也意味着芯片越好），同样的时间里能读进来的数据越多，tok/s 同样越高。

这就是为什么量化（减少每个权重的字节数）能直接换来速度，而不仅仅是省下磁盘空间。把这个关系写成公式，就是：

\[
\text{tok/s} \approx \frac{\text{内存带宽（字节/秒）}}{\text{参数量} \times \text{每权重字节数}}
\]

举一个具体的例子。一款中端手机 SoC 的有效内存带宽大约在 20 GB/s 这个量级。注意这里说的是“有效”带宽：芯片标称的理论带宽会更高，但实际跑起来通常只能用到三四成。现在让这块芯片运行一个 3B 模型，算一算理论上能跑到多少：

- **Q4_K_M（约 4.5 bpw，即每权重约 0.56 字节）**：\(\frac{20\text{ GB/s}}{3\times10^9 \times 0.56} \approx 11.2\ \text{tok/s}\)
- **FP16（每权重 2 字节）**：\(\frac{20\text{ GB/s}}{3\times10^9 \times 2} \approx 3.3\ \text{tok/s}\)（实际更低，约 2 个，因为还有其他开销）

把两个结果放在一起看，差别就非常清楚了：**同一块芯片，只是换一种更省字节的量化格式，速度就能差出好几倍**。这背后没有什么玄学，纯粹是带宽的算术。

如果不想每次都拿计算器，可以把这个公式写成一个很小的函数，随时估算任意模型、任意格式的端侧速度上限。下面三种语言的实现逻辑完全一致：输入内存带宽、参数量和每权重比特数，返回理论上的 tok/s。读的时候可以对照着看，它们算的是同一件事。

**C++：**

```cpp
#include <cstdio>

// 带宽单位：字节/秒；参数量：个；bpw：每权重比特数
double theoretical_tok_per_s(double bandwidth_bps, long long n_params, double bpw) {
    const double bytes_per_weight = bpw / 8.0;
    const double bytes_per_token  = n_params * bytes_per_weight;
    return bandwidth_bps / bytes_per_token;
}

int main() {
    const long long n_params = 3e9;             // 3B 模型
    printf("Q4_K_M (4.5 bpw): %.1f tok/s\n", theoretical_tok_per_s(20e9, n_params, 4.5));
    printf("FP16    (16 bpw): %.1f tok/s\n", theoretical_tok_per_s(20e9, n_params, 16));
    return 0;
}
```

**C#（.NET 5+）：**

```csharp
using System;

static class TokRate {
    static double TheoreticalTokPerS(double bandwidthBps, long nParams, double bpw) {
        double bytesPerWeight = bpw / 8.0;
        double bytesPerToken  = nParams * bytesPerWeight;
        return bandwidthBps / bytesPerToken;
    }

    static void Main() {
        const long nParams = 3_000_000_000L;          // 3B
        Console.WriteLine($"Q4_K_M (4.5 bpw): {TheoreticalTokPerS(20e9, nParams, 4.5):F1} tok/s");
        Console.WriteLine($"FP16    (16 bpw): {TheoreticalTokPerS(20e9, nParams, 16):F1} tok/s");
    }
}
```

**Python：**

```python
def theoretical_tok_per_s(bandwidth_bps: float, n_params: int, bpw: float) -> float:
    bytes_per_weight = bpw / 8.0
    bytes_per_token = n_params * bytes_per_weight
    return bandwidth_bps / bytes_per_token

n_params = 3_000_000_000  # 3B
print(f"Q4_K_M (4.5 bpw): {theoretical_tok_per_s(20e9, n_params, 4.5):.1f} tok/s")
print(f"FP16    (16 bpw): {theoretical_tok_per_s(20e9, n_params, 16):.1f} tok/s")
```

三种实现的输出完全一致。不过这个估算的局限也要说清楚。它只算了“读权重”这一项，没有算 KV 缓存、中间激活、解码开销和并行效率这些次要因素，所以真实速度通常会低于这个上限。但用来解释“为什么省字节能直接换速度”，以及在不同格式之间做相对比较，它已经足够好用了。

### 1.1.2 存储占用与冷启动延迟

量化带来的第二个好处，是让模型真正“装得下”。在展开之前，先区分两个经常被混着说的指标。它们看起来都像在说“占内存”，其实说的不是一回事：

- **文件体积（磁盘占用）**：模型文件在磁盘或存储卡上占多少空间，影响下载时间、存储卡占用和分发成本。
- **运行时 RSS（内存占用）**：推理进程实际吃掉的物理内存，影响这台设备能不能把模型跑起来、会不会因为内存不够被系统杀掉。

GGUF 有一个很巧妙的设计：用 **mmap（内存映射）** 来加载模型。它的做法是把文件直接映射进进程的地址空间，需要哪一块就读哪一块，**不必先把整个文件复制一份到内存里**。这样做带来一个直接结果：冷启动（也就是从点击图标到能吐出第一个 token 的那段时间）主要取决于首次读入时的缺页开销，以及页缓存里有没有现成的数据，而不是单纯取决于文件大小本身。对于 3B 模型，一个典型的端侧对比（不同来源的实测量级，取约数）是：

| 指标 | Q4_K_M（约 4.5 bpw） | FP16 |
|---|---|---|
| 文件体积 | 约 1.7 GB | 约 6.0 GB |
| 运行时 RSS | 约 2.1 GB | 约 7.2 GB |
| 端侧 tok/s | 约 11.2 | 约 2.1 |
| 冷启动 | 明显更快 | 明显更慢 |

这张表里有三件事值得停下来看一眼。第一，**Q4_K_M 用不到 1/3 的体积，却跑出了 5 倍以上的速度**。第二，RSS 比文件体积略大一些，因为推理时除了权重，还要给 KV 缓存和中间激活留出内存，这些东西并不全是权重。第三，冷启动的差异不仅来自文件大小，还来自 mmap 的页缓存效率：文件越小，越容易在缓存里被命中，第一次加载自然也就越快。

### 1.1.3 为什么"一种格式"打不了天下

既然 Q4_K_M 这么好，那所有模型都用它不就行了？答案是不行。因为不同场景对“精度和体积”的取舍完全不同，同一个位宽没法同时满足所有人：

- **手机、平板**：内存可能只有 4–8 GB，必须用 <2 bpw 的极限压缩（IQ 系列甚至三值格式），哪怕牺牲一部分质量，目标首先是“跑得动”。
- **工作站、服务器**：内存 64 GB 起步，完全可以承受 Q5_K 甚至 Q8_0 的“奢侈”，目标是“质量尽量接近原版”。
- **调试、研究、对比**：需要 Q8_0 甚至 F16 作为“参考基线”——拿它来衡量别的格式到底损失了多少，所以它本身不能再有明显损失。

打个比方：你不可能拿同一把刀既切西瓜又剔牙。**单一格式的困境就在这儿：无论选哪个位宽，都会在某个场景里要么浪费空间、要么牺牲质量。**

GGUF 给出的答案不是“折中出一个万能位宽”，而是**把选择权下放到每个张量**。在同一个文件里，注意力层可以用 Q4_K，输出层可以用 Q6_K，归一化层干脆保留 F32，各管各的。这正是第 3 章要讲的容器机制，也是第 14 章“逐张量混合精度”的由来。


## 1.2 量化术语的最小共识

### 1.2.1 块、超级块与 bpw 的定义

正式进入格式细节之前，先把三个最常出现的词确定下来。不然后面每走一步都要停下来解释，读起来会很累。

**块（block）**：一组共享同一个量化尺度参数的权重集合。这里说的“共享”，意思是这一组权重在存储时只保存一个公共的缩放系数，而不是每个权重各自带一个。为什么非要分块？因为一个张量内部的数值分布往往很不均匀：绝大多数值都挤在零附近，少数几个值又特别大。如果整个张量共用一个尺度，这个大尺度会被少数大值“绑架”，小值就可能被压成零，细节全丢了（第 4 章会把这个过程详细算给你看）。所以做法是把张量切成一段一段的连续小组，每组单独算自己的尺度。Q4_0 的块是 **32 个权重**，Q8_0 也是 32 个。

**超级块（super-block）**：K-quants 系列使用的一种更大的单元，包含 **256 个权重**，内部再分成 8 个 32 值的子块。超级块拥有自己的“全局尺度”，每个子块又拥有“局部尺度 + 局部最小值”，相当于在大集体里再分小集体。这是第 6、7 章的主题。

**bpw（bits per weight，每权重比特数）**：衡量压缩程度的核心指标。名字听起来像个现成的单位，其实是一个算出来的比值，算法有严格定义：

\[
\text{bpw} = \frac{\text{文件/块字节数} \times 8}{\text{权重数}}
\]

注意：**bpw 不是"量化码的位宽"**。举例来说，Q4_0 的码确实是 4 位，但每个 32 值块还要额外存 2 字节的尺度 `d`，所以实际 bpw 是 \(\frac{18 \times 8}{32} = 4.5\)。多出来的 0.5 bit/权重，就是尺度、最小值、码本索引这些“额外开销”摊到每个权重上的结果。**任何格式的 bpw 都要按字节数实算，而不是按“听起来是几比特”来猜。**

### 1.2.2 尺度、最小值偏移与零点

量化本质上是用有限个离散值去“代表”连续的数。比方说，你本来可以写任意小数，现在只允许从一张很短的清单里挑一个最接近的。怎么安排这张清单，有三种常见做法，也就是三种参数化方式：

1. **对称块量化（只有尺度）**，如 Q4_0、Q8_0：反量化公式是 \(y = d \cdot q\)，其中 \(d\) 是尺度，\(q\) 是有符号码。离散值围绕 0 左右对称地排开，正负两边一样密。
2. **非对称块量化（尺度 + 最小值）**，如 Q4_K 的子块：公式是 \(y = d \cdot q - m\)，多了一个最小值，或者说偏移量 \(m\)。它的作用是让整排离散值可以整体平移，从而更贴合“最小不为负、最大又偏在一侧”的分布。
3. **显式零点（zero point）**，如 Q4_1：显式地存一个“零点”，公式写成 \(y = d(q - z)\) 或者 \(y = d \cdot q + m\)。这里的零点要单独占字节，不像对称格式那样可以省掉。

这三种做法在**表示能力**和**字节开销**上各有区别。对称最省字节，但前提是分布近似对称；非对称和显式零点能多表示一个偏移，代价是要多花字节。后面会看到，选哪种结构，直接决定了某个格式擅长什么样的权重分布。

### 1.2.3 对称、非对称与"伪对称"——一个常见混淆

这里有一个新手特别容易绕晕的地方，值得单独停下来讲清楚。下面这两个格式看起来都带一个“偏移”，但它们的性质完全不同：

- **Q4_0 的 `q - 8`**：Q4_0 存的是无符号 4-bit 码 \(q \in [0, 15]\)，反量化时做 \(y = d(q-8)\)。这个“减 8”只是**解码端的固定平移**，作用是把无符号码变成近似的有符号码。它**不增加任何参数开销**：文件里没有任何地方存这个 8，它是写死在代码里的。所以 Q4_0 在数学上可以看成“零点固定为 8”的格式，但这个零点一分钱都不占。
- **Q4_K 的 `d_{\min} \cdot m_j`**：这是**逐子块学习出来的真实偏移**。每个 32 值子块都有一个 6-bit 的 \(m_j\)，它配合全局的 \(d_{\min}\)，形成这个子块自己的最小值。这个偏移**需要额外字节**（存在 `scales` 数组里），而且每个子块的值都可能不同。

一句话总结两者的区别：**"q-8"是免费的固定偏移，"dmin·m_j"是收费的逐块学习偏移**。这个区别看起来很小，却直接决定了两类格式的误差结构（第 4、7 章会分别展开）。


## 1.3 GGUF 在 llama.cpp 工具链中的位置

### 1.3.1 转换、量化、mmap 加载、推理：四阶段流水线

从 Hugging Face 上的一组权重文件，到你的手机上真正能跑起来，中间是一条分工明确的流水线。每一步只做一件事，做完再交给下一步：

```
四阶段流水线

  Hugging Face (safetensors / PyTorch)
        │
        ▼
  ① 转换  convert_hf_to_gguf.py
        │  只做"容器转换"，不做量化：把权重搬进 GGUF 容器
        ▼
  F16 GGUF 文件（约 14 GB，无损基线）
        │
        ▼
  ② 量化  llama-quantize（可选 + llama-imatrix 生成重要性矩阵）
        │  把每个张量压成目标格式，如 Q4_K_M
        ▼
  量化后 GGUF 文件（约 3.8 GB）
        │
        ▼
  ③ 加载  llama.cpp 运行时 mmap
        │  映射文件、读元数据、按张量类型分派解码路径
        ▼
  ④ 推理  逐 token 生成
```

这四个阶段各自负责一个“决策点”，谁也不替谁做决定：

- **convert_hf_to_gguf.py** 决定张量怎么命名、容器怎么组织（第 3、15 章）；
- **llama-imatrix** 决定“哪些权重更重要”——这是 IQ 系列格式能够工作的前提（第 11、15 章）；
- **llama-quantize** 决定每个张量具体用什么格式，也就是“混合精度策略”（第 14、15 章）；
- **运行时** 决定“每个 ggml_type 怎样解码、怎样交给后端执行”（第 16、17 章）。

### 1.3.2 GGUF 与 safetensors、PyTorch 的分工边界

GGUF 不是训练格式，也不是通用的交换格式。它和另外两个格式之间，边界需要说清楚，否则很容易把它们的用途搞混：

- **PyTorch / safetensors**：训练和微调时使用的格式。它们的目标是“灵活地保存任意张量、支持自动求导图的重建”，体积和加载速度不是首要考虑。
- **GGUF**：推理格式。它的目标是在三个约束下做到最优——**mmap 友好**（可以零拷贝加载）、**逐张量类型分派**（每个张量能选自己的量化格式）、**端侧推理**（体积小、解码快）。

GGUF 里那些看起来“奇怪”的设计——POD 结构体、固定对齐、type id 硬编码——都不是随手拍脑袋的结果，而是这三个约束的直接产物。第 3 章会逐一解释：为什么结构体必须是 POD（也就是一块只有数据、没有隐藏逻辑的内存结构，这样 mmap 之后可以直接当成内存里的结构体用）、为什么要有对齐（为了让每个张量都从对齐的位置开始）、为什么 type id 是硬编码的（为了运行时能快速分派到对应的解码函数）。

一句话概括：**safetensors 是“仓库”，GGUF 是“战时补给箱”**。一个是为了长期把东西存好，一个是为了在资源紧张的地方快速装卸。


## 1.4 量化范式的三次跃迁

全书的叙事主线是：量化格式并不是一堆平起平坐的选项，而是**沿着“解决上一个范式留下的问题”这条线，一步步演进出来的**。三次跃迁对应三组格式，每一组都解决了前一组解决不了的问题，同时也都付出了新的代价。

### 1.4.1 第一范式：块共享尺度的仿射量化（Q4_0 / Q8_0）

最朴素的做法是这样的：每个块（32 个权重）共享一个 FP16 尺度 `d`，权重本身存成 4-bit 或 8-bit 的码。它的优点是**实现简单、解码极快**，整个解码过程只有位操作和一次乘法，几乎没有额外负担。缺点是**块内异质性会惩罚小值**：如果一个块里同时存在很大的幅值和很小的幅值，尺度会被大值主导，小值就可能全部塌缩成同一个码（第 4 章会详细展示）。

```
第一范式：块共享尺度

  ┌─────────────┐
  │  32 权重共享 │  ← 一个尺度 d，一个公式 y=d·(q-8)
  │  1 个尺度 d  │
  └─────────────┘
  简单，但块内异质时小值被牺牲
```

### 1.4.2 第二范式：超级块内的层次化尺度与最小值（K-quants）

第二范式没有去改码的位宽，而是**改了尺度的结构**。它把 256 个权重放进一个超级块，超级块有全局尺度 `d` 和全局最小值尺度 `d_min`，内部 8 个 32 值子块则各自有 6-bit 尺度和 6-bit 最小值。于是误差预算从“一个尺度管全部”变成了“全局尺度打底，子块再各自修正”。

```
第二范式：超级块内的层次化尺度（K-quants）

  ┌──────────────────────────────────────────┐
  │ 超级块（256 值）：d、d_min                │
  │  ┌────┬────┬────┬────┬────┬────┬────┬──┐ │
  │  │子块0│子块1│...│子块7│   每个子块：       │
  │  │ s₀  │ s₁  │   │ s₇  │ 6-bit 尺度+最小值│
  │  └────┴────┴────┴────┴────┴────┴────┴──┘ │
  └──────────────────────────────────────────┘
  代价：多存 12 字节的参数；收益：块内异质不再由单一尺度承担
```

这一步解决了第一范式的核心失效：**块内异质性不再让单一尺度一个人“背锅”**。当然，代价是解码时多了一层解包工作（第 6、7 章会拆开讲）。

### 1.4.3 第三范式：重要性加权码本与三值结构化稀疏（IQ / STQ1_0 / PTQ1_0）

当位宽被压到 2 bpw 以下，第二范式也触顶了。均匀的码字覆盖不了重尾分布，层次化尺度也救不回来。第三范式于是换了两件新武器来突破：

- **码本（grid）+ 重要性矩阵（imatrix）**：不再依赖“尺度 × 码”这种算术公式，而是直接去查一张预先设计好的非线性表，也就是码本。同时，量化误差按“这个权重对输出的影响有多大”来加权，影响大的地方误差要小（IQ 系列）。
- **三值 + 结构化稀疏**：把权重硬性约束到只有 \(\{-d, 0, +d\}\) 三种取值，再用模式编码或者 base-3 编码把它存下来（STQ1_0 / PTQ1_0）。

```
第三范式：码本查表 + 三值稀疏

  第二范式:  y = d·s_j·q − d_min·m_j        ← 算术反量化
  第三范式:  y = d · grid[index]            ← 码本查表
             y = d · trit (∈{-1,0,+1})      ← 三值
```

这次跃迁的代价是**工程复杂度明显上升**：查表在 SIMD 上比算术公式更难实现，必须额外提供 imatrix，而且并不是所有后端都覆盖完整。这些问题会在第 11、13 章反复出现，读到那里时你会有更具体的感受。


## 本章小结与通往数值基础的桥梁

把本章的内容压缩一下，其实就三个事实。

**第一，端侧解码受内存带宽限制，所以量化能直接换速度。** roofline 模型告诉我们，自回归解码是一个带宽受限任务。于是“每个权重占多少字节”这个数字，既是体积指标，也是速度指标。Q4_K_M 用不到 FP16 三分之一的字节，换来端侧几倍以上的 tok/s。

**第二，量化语言里最小的词汇表是“块、超级块、bpw、尺度、偏移”。** bpw 要按“字节数 × 8 / 权重数”来算，不能按码的位宽来算；Q4_0 的 `q-8` 是不花钱的固定偏移，Q4_K 的 `d_min·m_j` 则是要花字节、逐块学习出来的真实偏移。

**第三，GGUF 不是某一种单一格式，而是“逐张量选择格式”的容器，位于转换→量化→加载→推理这条四阶段流水线的中间。** 三次范式跃迁（块尺度 → 层次化尺度 → 码本/三值）构成了全书的骨架。每一次跃迁都在解决上一次留下的失效，也都付出了新的代价。

下一章，我们就要开始“算账”了。量化到底损失了多少信息？误差是从哪里来的，又该怎么衡量？第 2 章会给出贯穿全书的分析工具：浮点表示、量化通式、误差分解，以及 PPL、KL、TTFT 这些评价指标。它们是后面每一个实验对比的裁判。
